## 问题标注清单

### 问题 #1: 系统代理故障导致联网预翻译功能误判不可用

**问题描述**  
Windows GUI 环境下 `urllib` 网络调用默认跟随系统代理（通过 `urllib.request.ProxyHandler` 读取 WinINET 注册表）。
当用户配置本机系统代理（如 fcclient 客户端的 `127.0.0.1:7892`）时,代理客户端重启、切换节点或抖动会导致该端口暂时无响应（连接被拒、socket 超时）。
屏译通的 `web_fetcher`（网页抓取与 robots.txt）、`network_monitor`（HTTP 探测）均使用 `urllib.request.urlopen`,将代理端点故障误判为"目标站点不可达",连续 3 次 timeout 后目标站点进入 COOLDOWN（300 秒冷却期）,预翻译功能实质停摆。

**出现位置/触发条件**
- **位置**: `src/pingyitong/services/prefetch/web_fetcher.py` 的 `fetch()` / `robots_allows()`,`src/pingyitong/services/prefetch/network_monitor.py` 的 `_probe_http()`
- **触发条件**:
  1. Windows 系统配置了本机代理（loopback 地址,如 `127.0.0.1:7892`）
  2. 预翻译功能开启,联网抓取触发网络调用
  3. 代理客户端（如 fcclient）重启、切换节点或短暂故障
- **环境依赖**: Windows + GUI 环境（CLI 启动因用户环境差异可能无此问题）

**影响范围**
- 直接影响: 联网预翻译功能（`web_fetcher`、`network_monitor`）
- 间接影响: 用户误以为自己网络环境不可用,或误判被抓取站点不可达,导致预翻译白名单配置不合理收窄
- 不影响: 在线 AI 引擎（`api_engine.py` 使用 `http.client` 直连,不经系统代理）

**当前严重程度**: **高**  
误判导致功能长时间（300 秒冷却）不可用,且日志中只显示 `timeout` / `网络错误`,无法直接定位根因为代理故障,用户体验差。

### 问题 #2: 最小字号 9px 渲染不清楚

**问题描述**  
原位翻译默认最小字号为 `9px`（`config.schema.StyleConfig.min_font_size` 与 `slot_layout.readable_font_size()` 硬编码）。
在桌面实测中,`9px` 日语汉字笔画（如"画面"）不清楚,部分笔画粘连或失真,可读性较差。
实机日志记录到最小 `9px` 场景,用户反馈紧凑布局下译文不易读。

**出现位置/触发条件**
- **位置**:
  - 配置 schema: `src/pingyitong/config/schema.py` `StyleConfig.min_font_size = 9`
  - 配置校验: `src/pingyitong/config/settings.py` `SettingsManager._validate_and_patch_config()` 允许 `min_font_size` 最小值为 `6`
  - 排版逻辑: `src/pingyitong/components/render/slot_layout.py` `readable_font_size()` / `allocate_slots()` 使用 `9px` 为兜底最小值
- **触发条件**:
  1. 原文区域极小（如密集小字行、系统托盘提示）
  2. 字号自动模式下根据原文高度推算的字号 < `12px`
  3. 用户未手动配置更大的固定字号
- **环境依赖**: 任意 DPI 和操作系统

**影响范围**
- 直接影响: 所有采用自动字号且原文区域高度小于 12px 高度阈值的原位翻译
- 不影响: 固定字号模式、文字栏（文字栏单独可控字号）

**当前严重程度**: **中**  
影响用户体验与可读性,但不导致功能失效；高 DPI 或正常字号布局无此问题。

### 问题 #3: `web_fetcher.fetch()` 中不可达重定向分支（已修复）

**问题描述**  
`fetch()` 内部使用 `_NoRedirect` 禁用自动重定向,手动逐跳跟进。
`_NoRedirect.redirect_request()` 返回 `None` 使得 `urllib` 将 3xx 状态抛成 `HTTPError`,因此 `opener.open()` 成功返回时 `response.status` 恒不为 3xx。
原代码在 `except HTTPError` 块之后又有一个 `if response.status in (301, 302, ...)` 分支（约 157–168 行）,该分支永远不会被执行（死分支）。

**出现位置/触发条件**
- **位置**: `src/pingyitong/services/prefetch/web_fetcher.py` 约 157–168 行
- **触发条件**: 该分支在任何情况下都不会被执行,因此无触发条件
- **环境依赖**: 无

**影响范围**
- 直接影响: 代码可维护性降低,逻辑混乱
- 不影响: 功能行为（该分支本就从未执行过,删除前后功能表现一致）

**当前严重程度**: **低**（已在 0.6.40 修复,仅记录用于完整性）

## 解决方案分析

### 问题 #1: 系统代理故障误判

**根因分析**  
`urllib.request.urlopen()` 默认通过 `ProxyHandler` 跟随系统代理。
当系统配置本机 loopback 代理且代理端点暂时故障时,连接失败（`ConnectionRefusedError` / `TimeoutError`）被误解读为目标站点不可达。
`api_engine.py` 使用 `http.client` 直连,未走系统代理,因此未受影响；但 `urllib` 路径无降级机制。

**解决方案类型**: 需修改代码或配置解决

**实施步骤**:
1. 新增模块 `src/pingyitong/utils/urlopen_proxy_safe.py`,封装带降级逻辑的 `urlopen_with_proxy_fallback()`:
   - 首次请求走默认 opener（跟随系统代理,保持兼容性）
   - 仅当首次失败且可明确归因于 loopback 代理端点故障时（条件：代理主机为 `127.0.0.1`/`localhost`/`::1`,且异常为 `ConnectionRefusedError`/`TimeoutError`）,使用 `ProxyHandler({})` 空代理直连重试**一次**
   - 远程代理、无代理配置、DNS 失败等非代理端点故障场景**不降级**,保持原异常抛出
2. 修改 `web_fetcher.py`:
   - `robots_allows()` 使用 `urlopen_with_proxy_fallback` 替代 `urllib.request.urlopen`
   - `fetch()` 内 `_open_noredirect()` 应用相同降级策略（需保持手动逐跳重定向语义）
3. 修改 `network_monitor.py`:
   - `_probe_http()` 使用 `urlopen_with_proxy_fallback`
4. 新增完整单元/集成测试 `tests/test_urlopen_proxy_safe.py`:
   - E2E 测试：真实 loopback http.server + mock 死代理端口 → 验证降级直连成功
   - 条件测试：无代理、远程代理、HTTP 站点回复、DNS 错误均不触发降级
   - 覆盖 `fetch()` robots + 重定向路径

**适用条件**:
- 用户配置本机 loopback 系统代理（远程代理或无代理用户无影响）
- 代理客户端偶发短暂故障（若代理客户端完全停止,降级直连可正常工作）

**潜在副作用**:
- 降级直连绕过代理,对于**必须经代理才能访问**的站点可能仍失败（降级逻辑仅适用本机代理端点故障场景）
- 增加一次额外请求（降级重试）,对于瞬时高频场景可能略增延迟（但仅触发于代理故障时,正常路径无额外开销）

**方案状态**: ✅ 已实现（当前未提交改动）

### 问题 #2: 最小字号 9px 不清楚

**根因分析**  
配置默认值与校验逻辑允许 `min_font_size` 最小为 `6px`,实际生产默认为 `9px`。
在高密度小字场景下,自动字号计算会降至 `9px`,日语/中文笔画细节失真。
Windows 桌面推荐最小字号为 `12px`（约 9pt）以保障可读性。

**解决方案类型**: 需修改代码或配置解决

**实施步骤**:
1. 修改配置 schema `src/pingyitong/config/schema.py`:
   - `StyleConfig.min_font_size` 默认值从 `9` 改为 `12`
2. 修改配置校验 `src/pingyitong/config/settings.py`:
   - `_validate_and_patch_config()` 中 `min_font_size` 校验下界从 `max(6, ...)` 改为 `max(12, ...)`
   - `font_size_fixed` 校验下界同步从 `max(6, ...)` 改为 `max(12, ...)`
3. 修改排版逻辑 `src/pingyitong/components/render/slot_layout.py`:
   - `readable_font_size()` 和 `allocate_slots()` 中硬编码兜底值从 `9` 改为 `12`
4. 校验旧配置兼容性:
   - 用户旧配置若手动设置 `min_font_size < 12`,加载后会被校验逻辑拉升至 `12`（降级保护,保障可读性）

**适用条件**:
- 任意操作系统与 DPI 配置
- 自动字号模式下原文区域较小的场景

**潜在副作用**:
- 极小原文区域（高度 < 12px 阈值）可能无法完整显示译文,会触发省略号
  - 缓解：译文完整内容仍保留在文字栏和复制结果中
- 用户旧配置中手动设置的 `min_font_size = 9` 会被强制提升至 `12`
  - 影响评估：旧 `9px` 本就不清楚,提升至 `12px` 属改善,非破坏性变更

**方案状态**: ✅ 已实现（当前未提交改动）

### 问题 #3: 不可达重定向分支

**根因分析**  
`_NoRedirect.redirect_request()` 返回 `None` 导致 `urllib` 将 3xx 抛成 `HTTPError`。
`fetch()` 的 `except HTTPError` 分支已正确处理 3xx 逐跳校验,`opener.open()` 成功返回时 `response.status` 不可能为 3xx。
该死分支 `if response.status in (301, ...)` 的 `if validate:` 门控与 `except` 分支无条件校验行为不一致,实际从未执行过。

**解决方案类型**: 需修改代码或配置解决

**实施步骤**:
1. 删除 `src/pingyitong/services/prefetch/web_fetcher.py` 约 157–168 行的死分支
2. 重定向逐跳校验统一由 `except HTTPError` 分支承担（已验证该分支覆盖所有 3xx 场景）
3. 新增回归测试 `tests/test_prefetch_p3.py`:
   - `test_redirect_to_loopback_blocked_even_without_validate`: 验证 `validate=False` 时 loopback 跳转仍被拒
   - `test_redirect_missing_location_error`: 验证 302 无 `Location` 头部时返回错误
   - 保持原有 `test_redirect_to_private_blocked` 通过

**适用条件**:
- 任意环境（纯代码清理）

**潜在副作用**:
- 无（该分支从未执行,删除前后功能行为完全一致）

**方案状态**: ✅ 已修复并发布（0.6.40）

## 附录：候选替换模型说明

本轮分析的 3 个问题均为基础设施、配置或代码逻辑问题,**与 LLM 模型无关**。

屏译通项目当前支持的翻译引擎包括:
- 本地 GGUF 模型（1.7B 极速 / 4B 高精度）
- 在线 API 引擎（OpenAI / Anthropic / Azure / 智谱 / 百川等）
- 本地 CTranslate2 NLLB 模型（探针阶段,未入产）

**模型更换对本轮问题的影响**: 无

若未来识别出**翻译质量**相关问题（如条件倒置、否定漏失、数字替换等语义错误）,可通过以下方式优化:
- 提示词改进（如 0.6.39 的 `relation_audit` 臂 A/B 研究）
- 切换更高精度模型（1.7B → 4B,或启用在线 API）
- 纠错守卫（如 0.6.29 新增的 temporal 时间关系守卫）
- 后备路线（1.7B 失败时自动调用已就绪 4B）
