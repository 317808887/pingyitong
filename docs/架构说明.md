### 1.2 依赖方向

**单向依赖，自下而上**：UI → 业务 → 核心 → 基础组件 → 支撑。

两个有意的例外，都在注释中标注了原因：

1. `core/pipeline.py` 依赖 Qt（`QObject` / `QTimer`）：
   渲染阶段必须在 Qt 主线程执行（Qt 控件只能主线程操作），
   因此流水线的渲染定时器由主线程驱动。
2. `components/render/` 依赖 Qt：渲染引擎本身就是 Qt 绘制，无法剥离。

**业务逻辑与核心算法不依赖 Qt** —— 这是有意的架构约束，理由是它让
"更换 GUI 框架"成为可控的迁移而非重写。考虑到 PyQt6 的 GPL v3 许可对
商业发布有传染性要求（详见 `LICENSE`），保留这条退路是必要的。

验证方式：

```bash
# 这两个目录不应出现 PyQt6 导入
grep -r "PyQt6" src/pingyitong/services/ src/pingyitong/core/task_queue.py
```

## 二、关键设计决策

### 2.1 线程模型：多线程而非多进程

**开发文档的要求**："整个流水线为多进程异步架构，各环节通过队列解耦。"

**实际实现**：多线程 + 队列。

**理由**：

| 考量 | 多进程 | 多线程（实际选择） |
| --- | --- | --- |
| **并行能力** | 真并行 | `onnxruntime` 与 `llama.cpp` 在计算时都释放 GIL，同样获得真并行 |
| **启动开销** | Windows 使用 spawn，每个子进程都要重新导入 PyQt6 与全部依赖（数秒） | 无额外导入开销 |
| **内存占用** | 模型权重需在每个子进程中各加载一份，内存成倍增加 | 权重只加载一份 |
| **数据传输** | numpy 图像需序列化跨进程拷贝，15fps 下 CPU 与内存带宽开销可观 | 传递引用，零拷贝 |
| **与 8GB 内存目标** | **直接冲突** | 满足 |

**保留的部分**：队列解耦、有界队列、背压策略、丢帧机制完全保留，
架构的分层与解耦特性不变。若未来需要真隔离（例如把 OCR 放进独立进程
以便崩溃后重启），`task_queue` 的接口设计已支持替换为
`multiprocessing.Queue`。

### 2.2 背压策略：丢旧保新

**规则**：队列满时丢弃**最旧**的数据，绝不阻塞上游。

**理由**：屏幕翻译的时效性远重于完整性。

- 延迟 2 秒的译文即使准确也没有价值——用户早已滚动到别处；
- 若阻塞上游，会让捕获线程停摆，画面变化被积压，恢复后一次性处理
  一堆过期帧，反而更慢；
- 若丢弃**最新**数据（另一种常见策略），则永远在处理历史内容，
  译文与屏幕内容持续错位。

**实现**：`LatestQueue` 提供三级语义

| 构造参数 | 语义 | 用于 |
| --- | --- | --- |
| `maxsize=2` | 容量 2，满时丢最旧 | 捕获队列 |
| `maxsize=3` | 容量 3，满时丢最旧 | OCR、翻译队列 |
| `keep_latest_only=True` | 永远只保留 1 条 | 渲染队列 |

渲染队列用"只留最新"是因为中间帧没有绘制意义：渲染层只画当前状态。

**额外机制**：`get_after(min_seq)` 会丢弃序号落后于指定值的过期数据。
这是"保证翻译结果始终对应当前屏幕内容"的直接实现——若队列里只有过期帧，
直接丢弃而不做无谓的推理。

### 2.3 双模型调度：三级 + 防抖

**三级优先级**：

```
一级 手动模式      用户显式选择 → 完全遵从，不做任何自动切换
      ↓ 未启用
二级 资源自适应    渲染帧率 < 10fps  → 降级到 1.7B（最高优先级）
                   CPU 持续 > 70%   → 降级到 1.7B
                   GPU 空闲 ≥ 2GB 且 CPU 低 → 升级到 4B
      ↓ 资源未触发
三级 内容自适应    长句（≥80 字符）或术语密度高 → 升级到 4B
                   短句（< 40 字符）            → 降级到 1.7B
                   中等长度                      → 沿用当前模型
```

**关键点：资源约束优先于内容偏好。** 长文本本应使用高精度模型，
但 CPU 已持续高负载时必须降级——宁可译文质量略降，也不能让用户的电脑卡顿。

**防抖三条**：

| 机制 | 值 | 解决的问题 |
| --- | --- | --- |
| 切换冷却 | 8 秒 | 模型反复"加载—卸载—再加载"（4B 加载需数秒，抖动比不切换更差） |
| 持续判定 | CPU 需持续 3 秒高于阈值 | 编译器、浏览器渲染等短时占满 CPU 造成误判 |
| 双击检查 | `ensure_loaded` 双重检查 | 并发请求下的重复加载 |

**一个曾经踩到的坑**（已在测试中固化）：
`_decide_by_resource` 最初在任何情况下都返回决策对象（资源正常时返回
"沿用当前模型"），导致 `decide()` 永远不会走到内容自适应——
只要调用方提供了资源快照（流水线总是提供），三级调度就退化成二级。
现在资源正常时返回 `None`，让流程继续下探。
`tests/test_config_and_scheduler.py::test_long_text_upgrades_to_accurate`
就是针对这一点的回归测试。

### 2.4 高 DPI 坐标对齐

**两套坐标系**：

| 坐标系 | 来源 | 单位 | 原点 |
| --- | --- | --- | --- |
| **物理坐标** | `mss` 捕获的位图 | 物理像素 | 虚拟桌面左上角（可能为负） |
| **逻辑坐标** | Qt 窗口与鼠标事件 | 设备无关像素 | 同上 |

**换算规则**（遵循 Qt `QHighDpiScaling`）：

```
逻辑坐标 = 屏幕物理原点 + (物理坐标 - 屏幕物理原点) / 缩放比例
```

**关键：屏幕原点本身不缩放，只缩放尺寸。**

**一个真实踩到的 bug**（已有回归测试）：
最初实现为 `逻辑坐标 = 物理坐标 / 缩放比例`，即把原点也除了一次。
在 150% 缩放的副屏上，副屏物理原点 1920 → 逻辑 1280，
而 Qt 实际报告的副屏逻辑原点是 1920。这导致：

- 按逻辑坐标查屏时点会落进主屏的逻辑范围，选错显示器；
- 渲染层计算"窗口内坐标"时把已经对齐的原点又减了一次，
  译文坐标为负、被推出窗口——**表现为"翻译层什么都不显示"**。

由于这种错误只在"多显示器 + 缩放比例不一致"时才会暴露，
普通单屏开发环境完全测不出来。因此 `tests/test_geometry.py` 中
专门构造了混合 DPI 的双屏环境做回归。

**跨屏区域的特殊处理**：`capture_region_physical()` 会把捕获区域裁剪到
单块显示器内。原因是跨屏矩形的位图会被显示器间隙破坏，宽高不再等于
逻辑宽度之和，后续所有坐标换算都会失准。

### 2.5 术语库：占位符替换而非提示词注入

**为什么不用"把术语表写进提示词"**：

1. 术语一多就挤占上下文窗口；
2. 大模型并不保证严格遵守提示词，长文本下尤其容易漂移；
3. 无法在事后验证术语是否真的生效。

**占位符方案**：

```
原文: "We use GPU for machine learning"
  ↓ 替换（长术语优先）
"我们使用 [TERM_0] 进行 [TERM_1]"
  ↓ 模型翻译（只需原样搬运占位符）
"我们使用 [TERM_0] 进行 [TERM_1]"
  ↓ 还原
"我们使用 图形处理器 进行 机器学习"
```

**占位符字符选择**：使用 `[TERM_0]` 一类可读标记。实测极速模型会把旧的 Unicode 私用区标记误写成数字，而可读标记能完整保留。

**兜底机制**：还原阶段检测占位符是否缺失。缺失时：

1. 记录日志（可监控模型遵守约定的比例）；
2. **清除残留的占位符标记**——宁可少一个术语，也不能让
   `[TERM_0]` 这种乱码出现在用户屏幕上（看起来像程序崩溃）。

**匹配顺序**：术语按长度倒序排列。否则 `machine learning` 会被
`machine` 提前命中，拆成"机器 learning"，术语一致性随之失效。

### 2.6 翻译的批量与降级

**批量**：多个文本片段合并为一次推理请求，用 `<<<SEG>>>` 分隔。
桌面场景下片段通常很短（菜单项、按钮文案），逐条推理的固定开销
（上下文准备、采样初始化）远大于生成开销，批量能显著提升吞吐。

**降级**：批量请求只要模型少输出一个分隔符，整批结果就会错位。
因此：

```
批量请求 → 解析输出
  ├─ 片段数匹配 → 采用
  └─ 片段数不匹配 or 请求失败
       └─ 逐条重试（慢但结果正确）
            └─ 单条也失败 → 保留原文（绝不留空白）
```

**"保留原文"这个兜底很重要**：若失败时返回空字符串，渲染层会在原文
位置画一个空白遮罩，把原文盖住却什么也不显示——用户会以为屏幕坏了。
保留原文至少保持可读。

### 2.7 单实例：命名互斥体而非套接字

**为什么不用本地 socket**：本项目以"全离线"为核心卖点，
任何形式的本机网络监听都可能在审计中被误判为网络行为。
命名内核对象（`CreateMutexW` / `CreateEventW`）是纯本机内核对象，
隐私边界清晰。

**唤醒机制**：第二个实例通过命名事件唤醒第一个实例，第一个实例在
后台线程中 `WaitForSingleObject` 接到信号后，通过 Qt 信号
（跨线程自动队列化）切回主线程打开面板。这解决了"用户忘了程序还在
后台运行、反复双击图标却没反应"的困惑。

### 2.8 全局热键：系统注册而非键盘钩子

**为什么不用 `keyboard` / `pynput`**：

1. 这类库普遍通过全局键盘钩子实现，会被安全软件拦截；
2. 全局键盘钩子会接收**所有**按键，对"隐私优先"的离线工具是不可接受的
   攻击面扩展——用户无法验证我们没有记录按键。

`RegisterHotKey` 是系统级注册，只通知注册过的那几个组合键，
不监听按键内容，隐私边界清晰。

**线程约束**：Windows 的 `RegisterHotKey` 把 `WM_HOTKEY` 投递到**调用线程**
的消息队列，因此注册与 `GetMessageW`/`PeekMessageW` 必须在同一线程。
回调在热键线程中触发，`Application._on_hotkey` 只做一件事：
通过 `pyqtSignal` 转发到主线程，绝不直接操作 Qt 控件。

**部分失败的处理**：热键可能被其他程序占用。注册失败时记录到
`HotkeyBinding.error`，界面可展示冲突提示，而不是让用户困惑于
"为什么热键没反应"。

### 2.9 配置：向前兼容与主动清洗

**向前兼容**：`from_dict()` 对缺失字段回落默认值，对未知字段静默忽略，
对类型错误回落默认值。这样：

- 用户升级程序后，旧配置文件（缺新字段）能正常加载；
- 用户降级程序后，新配置文件（含未知字段）也不会导致崩溃。

**主动清洗**：`SettingsManager._sanitize()` 在加载和保存时都会纠正越界值。
手工编辑配置文件写入 `fps: 9999` 或 `bg_opacity: 5.0` 时，
不能让非法值流入捕获与渲染链路。

**语言选择保留用户意图**：源语言与目标语言相同时也保存用户显式选择，
这样先选择源语言、再改变目标语言时不会意外丢失源语言。
翻译服务判断正文是否已是目标语言：同语正文保持原文，夹杂外语的段落继续翻译。

### 2.10 模型权重加载：多位置查找 + 后台预加载

#### 为什么查找多个位置

权重可能出现在三种场景，程序都应能找到，而不是要求用户把文件
搬到某个固定位置：

| 顺序 | 位置 | 场景 |
| --- | --- | --- |
| 1 | `$PINGYITONG_MODELS_DIR` | 用户自定义（如权重放在大容量数据盘） |
| 2 | `<项目目录>/models/` | 源码运行、评审机、打包分发 |
| 3 | `%LOCALAPPDATA%\PingYiTong\models\` | 便携模式、安装后的用户级数据目录 |

`resolve_model_path()` 的匹配策略由严到宽逐级放宽：

1. **精确文件名**；
2. **大小写不敏感**——官方发布的是 `Spark-X2.5-1.7B-Q4_K_M.gguf`，
   用户在 Windows 上常改成小写；
3. **参数量特征匹配**——从 Ollama / LM Studio 下载的文件名形如
   `spark-x2.5-1.7b-q4_k_m-00001-of-00001.gguf`，仅凭名字不等就
   判定"未找到"是错误的。特征匹配用正则提取 `1.7b` / `4b`，
   并限定 `.gguf` 后缀，同时**必须防止把 4B 的文件当成 1.7B**
   （会导致显存/内存耗尽），因此特征串必须严格匹配参数量。

全部落空时返回**期望路径**而非随机占位路径——上层据此在提示里
告诉用户"应该放到哪里"，而不是给一个莫须有的位置。

#### 为什么预加载必须异步

加载 1.7B 需要数秒、4B 需要十余秒。若在主线程执行，Qt 主线程被占用时
窗口无法重绘、按钮无响应，用户会认为程序卡死。

因此 `preload_async()` 在后台线程中执行，并通过回调汇报进度；
界面层用 Qt 信号把回调切回主线程再更新控件
（`preload_progress` / `preload_finished` 两个信号）。

同时延迟 300ms 再启动下载：让主窗口先完成首帧绘制。否则即使加载在
后台线程，磁盘密集读取仍会与界面初始化争抢 IO，用户感知到的
"启动慢"正是这个。

#### 哪些模型会被预加载

由各模型的 `preload` 字段决定，而非硬编码：

- **1.7B 默认预加载**：常驻模型，首次翻译几乎必然用到，
  预加载把"第一次翻译的等待"提前到启动阶段；
- **4B 默认不预加载**：占用约 2.8GB 内存，在 8GB 机器上与系统争抢内存
  反而拖慢整体，因此保持"首次使用时加载 + 空闲 180 秒卸载"。
  内存充足时用户可显式开启。

`preload_targets()` 还会**跳过权重缺失的模型**：否则启动时要去等一个
必然失败的加载，用户白等数秒却只得到一个错误提示。

#### 权重缺失时的降级

引擎创建时若发现权重或依赖缺失，降级为 `LayoutPreviewEngine`：

- 它按原文长度生成等长的占位标记 `〔未加载模型〕原文`；
- 长度与原文同量级，因此能**真实反映"译文撑不撑得下原文包围盒"、
  "多行如何换行"这类排版问题**——这正是渲染层最需要验证的部分；
- 界面在状态条、托盘提示与通知中明确标注"预览模式"，
  **不把占位内容伪装成翻译结果**。

### 2.11 双推理后端：为什么必须支持外部进程

#### 问题：模型架构不在上游 llama.cpp 里

Spark-X2.5 的 GGUF 元数据声明 `general.architecture = spark2_5`。这个架构
**只存在于 `XHToken/llama.cpp` 分支**，上游 `ggml-org/llama.cpp` 不认识它。

而 `llama-cpp-python` 捆绑的是上游 llama.cpp，因此它加载 Spark-X2.5 时
在模型加载阶段直接失败（实测 0.3.35）：

```
llama_model_load: error loading model: unknown model architecture: 'spark2_5'
```

关键判断：**这不是版本新旧问题**。架构支持只在分支里，升级
`llama-cpp-python` 的版本不会有任何改变。因此必须引入外部进程后端。

#### 方案：llama-server + 本机回环

```
┌──────────────┐   HTTP over 127.0.0.1    ┌────────────────────┐
│  屏译通进程   │ ───────────────────────► │ llama-server 子进程 │
│              │   /v1/chat/completions    │  (XHToken 分支构建) │
└──────────────┘ ◄─────────────────────── └────────────────────┘
        拉起 / 终止                                加载 GGUF 权重
```

后端自动探测，优先级为 `llama-server` > `llama-cpp-python`。把外部进程
排在前面是因为它是 Spark-X2.5 唯一可行的方式，且不受 Python 版本与编译
环境影响；进程内后端保留给架构受上游支持的其它模型。

#### 关于"全离线"的准确表述

该后端会在本机回环地址上开一个端口，这是**与本程序自己拉起的子进程之间
的进程间通信**，不涉及任何外部网络。程序仍然不发起任何对外网络请求。

文档与界面统一使用"不发起对外网络请求"这一表述，而不用"零网络"——
后者会被理解为"不创建任何套接字"，与本实现不符。**精确表述比漂亮的
口号重要**，尤其是在隐私这个核心卖点上。

#### 实测踩到的三个坑

这三个都是只有真正跑起来才会暴露的问题，已全部处理并固化为测试：

**坑 1：GGUF 权重不含 chat template。**
`tokenizer.chat_template` 在权重里是缺失的。走原始补全接口时模型看到的是
裸文本，输出退化成 `"As As As As…"`、`"SettingsSettings…"` 这类重复片段。
改用对话接口并传入随附的官方模板后正常。

**坑 2：llama.cpp 无法打开非 ASCII 路径的模板文件。**
在中文目录下启动报 `failed to open file 'F:\讯飞\...\spark-x2.5.jinja'`，
而**模型权重在同一个中文目录下却加载正常**——因为模型加载走宽字符路径，
模板读取走窄字符（ANSI）路径。解决方式是把模板复制到纯 ASCII 的临时目录；
注意目录名与文件名都必须是 ASCII，只改目录不改文件名同样会失败
（这条是单元测试发现的）。

**坑 3：模型是推理模型，默认会先"思考"。**
Spark-X2.5 默认先输出思考过程，答案放在 `reasoning_content`。实测同一句话：
关闭思考约 0.1 秒，开启约 0.6 秒。桌面实时翻译需要即时响应，因此默认关闭。
另外当 `max_tokens` 被思考过程耗尽时 `content` 会是空的——此时回退使用
`reasoning_content`，因为返回空字符串会让渲染层在原文位置画一个空遮罩
（用户会以为屏幕坏了）。

#### 预热：把首次推理的开销提前

模型加载完只是把权重读进内存。第一次真正的前向计算仍要付出可观开销
（图构建、KV 缓存分配、后端内核初始化）。实测数据：

| 阶段 | 耗时 |
| --- | --- |
| 加载 1.7B 权重并启动服务 | 2.0–3.1 秒 |
| **首次推理（未预热）** | **11–21 秒** |
| 之后每句翻译 | 0.06–0.11 秒 |

若不预热，这笔十几秒的开销会落在用户点"开始翻译"之后的第一帧上——用户
会以为程序卡死。因此 `ensure_loaded()` 在加载后执行一次极短推理（输入
`"."`、输出 8 token），把开销提前到启动预加载阶段（后台线程，不阻塞界面）。

预热状态会随卸载清除：否则 4B 空闲卸载后重新加载会跳过预热，用户就要
再承担一次首帧延迟。

OCR 也有同样问题：RapidOCR 首次调用要加载 ONNX 模型（实测 5.7 秒），
因此在预加载阶段一并预热。

## 三、数据流

### 3.1 完整链路

```
[捕获线程]
  mss 抓取 → CaptureFrame(seq, timestamp, image, origin)
       ↓ 画面差分（仅在变化时继续）
  changed_regions = [Rect, ...] 或 is_full_frame=True
       ↓ frame_queue.put(seq=...)          【容量 2，丢旧保新】
[OCR 线程]
  按变化区域裁剪 → 小字号增强 → RapidOCR 识别 → 坐标还原
       ↓
  RecognizedFrame(blocks=[TextBlock(text, box 物理坐标, confidence)])
       ↓ ocr_queue.put(seq=...)
[翻译线程]
  TextPreprocessor.process():
      过滤噪声 → 去重 → 按垂直重叠聚行 → 合并行内相邻块
      → 按间距划分段落 → 拼接文本（含断词修复）
       ↓ Paragraph(text, box=各块并集, language)
  语言判定（源==目标 → 跳过）
       ↓
  Glossary.substitute()  →  术语替换为占位符
       ↓
  TranslationCache.get()  →  命中则直接返回
       ↓ 未命中
  ModelScheduler.decide()  →  三级调度选定模型
       ↓
  ModelPool.translate()  →  批量推理（分隔符对位，失败降级逐条）
       ↓
  parse_response()  →  校验片段数
       ↓
  Glossary.restore()  →  还原术语，清除残留占位符
       ↓
  RenderFrame(items=[RenderItem(box 物理坐标, text 译文)])
       ↓ result_queue.put(seq=...)         【容量 3，只留最新】
[主线程渲染]
  QTimer(25ms) → get_latest()
       ↓
  OverlayManager.apply():
      按物理坐标归属分屏 → 每屏物理坐标 → 窗口内逻辑坐标
       ↓
  OverlayWindow.paintEvent():
      layout_text() 自适应字号与折行 → 绘制遮罩 → 绘制文字
```

### 3.2 时序特性

下表为**本机实测值**（24 核 / RTX 5070 Ti Laptop / Vulkan 后端 /
1.7B Q4_K_M / Windows 11），非估算：

| 阶段 | 实测耗时 | 说明 |
| --- | --- | --- |
| 模型加载（1.7B） | 2.0–3.1 s | 启动预加载阶段完成，不阻塞界面 |
| **首次推理（含预热）** | 11–21 s | **已提前到启动阶段执行** |
| 逐句翻译（1.7B，关闭思考） | 0.06–0.11 s | 稳态表现 |
| 逐句翻译（1.7B，开启思考） | 0.53–0.81 s | 约慢 6 倍 |
| OCR 预热（启动阶段） | 1.1–3.2 s | ONNX 会话初始化 |
| **OCR 整屏 2560×1600（59 块）** | **0.97 s** | 线程优化后；优化前 5.89 s |
| **OCR 局部 1100×500（15 块）** | **0.31 s** | 差分后的真实单帧负载 |
| 画面差分 | 2–8 ms | 与变化面积相关；无变化时为 0 |
| 渲染 | 1–5 ms | 与条目数量相关 |

**端到端延迟**：静置界面接近 0（差分判定无变化，整条链路不动）；
首帧约 3 秒（整屏 OCR + 首句翻译）；**增量帧约 0.4 秒**
（局部 OCR 0.31 s + 翻译 0.1 s），达到实时可用水平。

### 3.3 OCR 性能：线程数是关键

实测发现 RapidOCR 的默认 onnxruntime 线程配置在本负载下**严重偏低效**。
同一张 2560×1600 截图（74 个文本块）：

| intra-op 线程数 | 耗时 |
| --- | --- |
| 默认（不指定） | 5.89 s |
| 1 | 8.08 s |
| 2 | 4.73 s |
| 4 | 3.00 s |
| **8** | **2.25 s** |
| 12 | 2.28 s |
| 16 | 2.62 s |

**原因**：OCR 的识别阶段要逐个处理几十个文本块，每块的推理输入都很小
（约 100×32 像素）。线程过多时**线程同步开销反超计算收益**，因此存在
一个最优值而非"越多越快"。

另一个反直觉的观测：把整幅图像缩小 7 倍（像素少 6.8 倍）只让耗时降低
35%。这说明**瓶颈不在检测阶段的像素量，而在识别阶段的块数量**——
因此优化的正确方向是"减少送入识别的块"（画面差分正是这么做的），
而不是"缩小图像"。

自动值取 `min(8, 物理核数)`，配置项为 `ocr.threads`（`0` 表示自动）。

## 四、错误处理与降级

本项目的一条基本原则：**任何单点失败都不应导致程序崩溃或界面异常**，
而应降级到可用的状态并把原因告知用户。

| 失败点 | 处理方式 | 用户可见表现 |
| --- | --- | --- |
| 未安装 `mss` | 捕获器不可用，流水线拒绝启动 | 通知"未安装 python-mss，无法捕获屏幕" |
| 未安装 RapidOCR | OCR 返回空结果 | 通知"未安装 RapidOCR，无法识别屏幕文字" |
| 未安装 llama-cpp-python | 使用 `LayoutPreviewEngine` | 托盘提示"预览模式"；译文显示 `〔未加载模型〕原文` |
| 模型权重缺失 | 同上 | 设置面板模型状态显示"未就绪" |
| 模型加载失败（内存不足等） | 记录日志，返回空 | 该帧保留原文 |
| 单帧 OCR 异常 | 捕获异常，跳过该帧 | 无感知 |
| 单帧翻译异常 | 捕获异常，跳过该帧 | 无感知 |
| 批量翻译对位失败 | 降级逐条重试 | 延迟略增，结果正确 |
| 单条翻译失败 | 保留原文 | 原文位置显示原文而非空白 |
| 术语占位符缺失 | 清除残留，记录日志 | 该术语使用模型输出，无乱码 |
| 配置文件损坏 | 备份后回退默认配置 | 设置回到默认，程序正常启动 |
| 热键被占用 | 记录冲突，其余热键正常 | 设置面板显示冲突提示 |
| 屏幕捕获连续失败 5 次 | 停止流水线 | 通知"屏幕捕获连续失败，已停止" |
| 显示器拔掉 | 移除对应翻译层；悬浮条回退默认位置 | 无感知 |

**"预览模式"的设计说明**：
在模型未就绪时不静默失败，而是进入明确标注的预览模式。
它按原文长度生成等长的占位标记，因此可以**真实反映"译文撑不撑得下
原文包围盒""多行如何换行"等排版问题**——这正是渲染层最需要验证的部分。
界面顶部与托盘提示会明确标注，不会把占位内容伪装成翻译结果。

## 五、性能与资源

### 5.1 内存预算（8GB 机器）

| 组件 | 常驻占用 |
| --- | --- |
| Python + PyQt6 | ~120 MB |
| RapidOCR（ONNX Runtime） | ~180 MB |
| 1.7B Q4_K_M 模型 | ~1.2 GB |
| 4B Q4_K_M 模型（按需加载） | ~2.8 GB |
| 捕获帧缓冲（2 帧 × 双屏） | ~50 MB |
| **典型合计（仅 1.7B）** | **~1.6 GB** |
| **峰值（两个模型同时加载）** | **~4.4 GB** |

因此 4B 采用懒加载 + 空闲 180 秒自动卸载。`ResourceMonitor`
还提供 `recommend_model_for_memory()`：内存 < 15GB 时推荐仅用 1.7B。

### 5.2 GPU 加速

设置 `model.*.n_gpu_layers > 0` 可把部分层卸载到 GPU。
需要 `llama-cpp-python` 在编译时启用 CUDA：

```bash
set CMAKE_ARGS=-DGGML_CUDA=on
pip install llama-cpp-python --no-binary llama-cpp-python --force-reinstall
```

GPU 显存监控依赖 `pynvml`（可选）。未安装时资源自适应退化为
仅依据 CPU 与渲染帧率决策。

### 5.3 帧率动态控制

`CaptureConfig.adaptive_fps` 预留了按负载调整捕获帧率的开关。
当前实现中，系统负载通过**调度降级**来缓解（切换到 1.7B），
而非降低帧率——因为降低帧率会让画面变化被漏掉，用户感知更差。

### 6.3 静态导入检查

`scripts/check_imports.py` 在不导入任何依赖的前提下，通过 AST 解析检查：

1. 相对导入的目标模块文件是否存在；
2. `from x import y` 中的名字是否确实在 `x` 中定义或导出。

它解决的具体问题：PyQt6、onnxruntime 等依赖在评审环境中可能不存在，
无法用 `import` 验证；而包内相对导入的路径极易因重构而写错
（`..services` 写成 `.services`），这类错误只在运行时暴露。
本项目开发过程中该脚本发现并修正了 13 处导入问题。

### 6.4 界面异常不得终止进程

**现象**：用户点击「框选区域」，在屏幕上拖出选框，松开鼠标后程序**直接消失** ——
没有报错弹窗、日志里没有任何记录、任务管理器里进程已经不在。

**根因**有两层，缺一不可：

1. *触发点*：`RegionSelector` 的选区是 Qt 的 `QRect`，而项目自己也有一份
   `Rect`。两者的宽高访问方式**不同** —— Qt 用方法 `rect.width()`，
   本项目用属性 `rect.width`。换算逻辑写成 `selection.width` 后，
   传进 `Rect` 的是"方法对象"而不是数字。`dataclass` 不做类型检查，
   构造时不报错，直到后续做算术（`intersection` 里的整数加法）才抛
   `TypeError: unsupported operand type(s) for +: 'int' and 'builtin_function_or_method'`。

2. *放大器*：PyQt6 对"Python 重写的槽/虚函数里抛出未捕获异常"的处理方式是
   调用 Qt 的 `qFatal()` —— 进程立即终止（实测退出码 `0xC0000409`），
   **不打印堆栈、不写日志、不提示界面**。因此一个笔误 = 程序无声死亡。

**修复**：

- `_selection_logical()` 成为**唯一**把 Qt 选区转成本项目矩形的出口，
  换算只写一处，其余代码只面对一套 API；`mouseReleaseEvent` 与
  `keyPressEvent` 都走 `_confirmed_selection()`，保证鼠标与键盘两条提交
  路径的校验完全一致（此前只有鼠标那条检查了最小尺寸）。
- 新增 `pingyitong/utils/exceptions.py`，安装 `sys.excepthook`、
  `threading.excepthook` 与 `sys.unraisablehook`。装上后 PyQt6 会改为调用
  `sys.excepthook`，进程不再自杀；异常写入日志，并经 `exception_reported`
  信号（队列连接）转发到主线程弹提示。**提示明确写"操作未完成"**，
  避免用户误以为操作成功。

**验证**：该缺陷用 `scripts/repro_region_crash.py` 可复现 —— 修复前进程
在 `mouseRelease` 后消失且无任何 Python 栈，修复后完整走完拖拽、取消、
空绘制三条路径并以退出码 0 结束。

### 6.5 分层依赖方向必须可检查

`docs/架构说明.md` 一·1.2 规定依赖只能自上而下。实际开发中翻译 Prompt
需要语言名称表，而语言表当时放在 `services/languages.py`，于是
`components/llm/prompt.py` 反向依赖业务层，形成
`components → services → components` 循环，表现为单独导入组件层即报
`ImportError: cannot import name 'TranslationCache' from partially initialized module`。

修法不是绕开循环（延迟导入之类），而是让语言表回到正确位置：它是**数据**，
与 `constants.py` 同级放在包根 `pingyitong/languages.py`，各层都可引用。
`tests/test_layering.py` 用 AST 静态检查各层导入方向，并用子进程验证
语言表与 Prompt 模块可以**独立导入**。

### 6.6 框选区域模式的三处缺陷

用户反馈"**选框选取后，开启翻译，并没有进行翻译**"。排查下来是三个独立问题
叠在一起：前两个让人看不到正确结果，第三个让人不知道该看什么。
其中**缺陷三才是"翻译层始终一片空白"的真正原因**，也最难定位——
状态栏的帧率与延迟全都正常，看上去一切都在跑。

**缺陷一：框选区域被当作物理坐标使用。**

``RegionSelector`` 给出并存进配置的是**逻辑坐标**（已按 Windows 缩放折算），
而 ``ScreenCapturer.capture_region`` 要的是**物理坐标**。流水线直接把逻辑值
传了过去，于是 150% 缩放的主屏上：

.. code-block:: text

    配置里存的（逻辑）: 269, 9, 1068, 852
    实际应该捕获（物理）: 404, 14, 1602, 1278   ← 用户真正框选的区域
    修复前实际捕获:       269, 9, 1068, 852     ← 少截一大圈，且整体偏移

``CoordinateMapper.capture_region_physical`` 本来就是为这件事写的，
但**从未被调用过**（只有测试在调）。现在流水线持有映射器并在捕获前换算，
显示器变化时通过 ``refresh_screens()`` 刷新缓存。

顺带修掉了该函数内部的一份重复实现：它自己写了一遍 ``x * ratio``，
而正确规则是"屏幕原点不缩放、只缩放尺寸"（见 2.4）。两份实现只在物理原点
为 0 的屏幕上结果相同，接副屏就会偏移。现在直接复用 ``logical_to_physical``。

**缺陷三（主因）：译文条目在渲染阶段被整体丢弃。**

框选区域的捕获写死了 ``monitor_index=None``：

.. code-block:: text

    ScreenCapturer.capture_region() → _grab(monitor, monitor_index=None)
    → CaptureFrame.monitor_index = None
    → RecognizedFrame.monitor_index = None
    → Paragraph 没有这个字段（getattr 取到 None）
    → RenderItem.monitor_index = None

而渲染阶段按显示器分发条目（这样多屏时各块屏幕只画自己的译文）：

.. code-block:: code

    if active_monitor_indices and item.monitor_index not in active_monitor_indices:
        continue          # None not in {1} → 全部丢弃

框选后 ``capture.monitors`` 被写成 ``[1]``，于是 ``active_monitor_indices = {1}``，
而所有条目的序号都是 ``None`` —— **一条都画不出来**。

**为什么极难发现**：流水线本身完全正常。OCR 在识别、模型在推理、
``_render_tick`` 也在按 1fps 调用 ``apply()`` 并记录延迟与帧率——
那些统计只统计"调用过"，不统计"画了几条"。所以状态栏显示
``捕获 30fps · OCR 1fps · 渲染 1fps · 延迟 50ms``，看上去健康得很，
屏幕上却什么都没有。最初甚至据此误判为"翻译已经在工作"。

**修复两处**，一处补数据、一处改判据：

1. ``capture_region`` 增加 ``monitor_index`` 参数，由流水线（持有坐标映射）
   判定区域落在哪块屏幕上并传入；``Paragraph`` 补上 ``monitor_index`` 字段，
   由 ``TextPreprocessor.process`` 从捕获帧一路带下来，
   使条目携带**正确**的显示器序号。
2. 渲染过滤改为**序号未知时不参与过滤**（失败开放）。缺少字段是数据问题，
   不该演变成"整屏都不画"：宁可多画一条，也不要静默丢掉全部。

回归测试见 ``tests/test_region_capture.py::TestMonitorFiltering``
与 ``TestParagraphMonitorIndex``。

**缺陷二：整帧没有可见变化时毫无说明。**

用户的目标语言是中文，而被框选的窗口内容本身就以中文为主，
于是"译成中文"的结果与原文几乎一致，屏幕上看起来**什么都没发生**。
程序完全静默，用户只能认为软件坏了。

这里有一个反直觉之处值得记下来：**不能按"统计上有没有翻译"来判断**。
实测抓到的真实数据是 17 段里"译了 4 段、跳过 13 段"——那 4 段是被判为英文的
路径与代码片段，模型按要求原样保留（这是 Prompt 第 3 条硬性要求），
译出来与原文一模一样。统计上"翻译过了"，用户看到的仍是"什么都没变"。

因此判据改成**比较译文与原文**：整帧所有条目都与原文相同（忽略空白差异）
才提示，且明确告诉用户原因与下一步怎么做（"请在设置中把目标语言改成
中文之外的语言"）。提示带 **60 秒冷却**：屏幕上只要有一小块内容在变
（光标闪烁、时钟走动），判断结果就会来回翻转，实测 9 秒内弹了两次；
更换目标语言属于用户主动操作，立即提示。

**验证**：``scripts/diagnose_region.py`` 打印逻辑/物理两种捕获范围与各自
识别到的文字；``scripts/verify_region_translation.py`` 走完整链路并检查
渲染条目是否落在框选范围内（修复后 17/17 全部落在范围内）。

### 6.7 语言选择框：从"可搜索输入框"退回普通下拉框

语言表有 142 项，当初为了查找方便做成了"可编辑 + 补全器"的搜索框。
用户实际用起来却卡住了：**点文本框没有任何反应**，只有右侧那条约 22px 的
箭头区域能展开列表，而箭头本身又因为样式表去掉了 `::drop-down` 边框而
不再绘制——界面上看不出这里是个可选列表，用户看到的只是一个空格子。

问题不止于此，可编辑下拉框还带来两个不一致：

- 键入的关键字**接在**现有标签后面（变成"✓ 中文（简体） · 简体中文Icelandic"），
  既搜不到东西，失焦后还会被判为无效输入而弹回原选择；
- 用户随手改动的文字与真实生效的语言会**对不上**——配置里存着中文，
  框里却显示空的或半截字样。

**改法是把控件换回普通下拉框**，而不是继续给搜索框打补丁：

- 非可编辑下拉框点控件任意位置都会展开列表，这是 Qt 的原生行为；
- 框里显示的永远等于当前选中项，"空格子"与"文不对题"从根上消失；
- 快速查找改由重写 :meth:`LanguageCombo.keyboardSearch` 承担。
  默认实现按**显示文本前缀**查找，而显示文本以状态符号 ``✓`` 开头、
  所有项都一样，等于完全失效；重写后在中文名、英文名、母语名与代码中
  查找，键入 ``冰`` / ``ice`` / ``is`` 都能跳到冰岛语。

这是"**给一个从固定清单里挑一个的操作套上自由输入框**"的典型代价：
输入框能表达的状态比操作本身多得多，多出来的状态就是不一致的来源。

回归测试见 ``tests/test_design_system.py::TestLanguageCombo``，
覆盖"点击任意位置展开列表""显示内容永远等于当前选择""三种名字都能跳转"
等实际踩过的点。

### 6.8 强制结束程序会留下占资源的孤儿进程

用户反馈"**开始后 GPU 吃满了但是在做无用功，页面还是没翻译**"。
截图显示 GPU 3D 利用率 99%、专用显存占满、共享 GPU 内存 17.9 GB、
系统内存 28.0/31.4 GB（89%）。看上去模型在拼命算，实际一个字都翻不出来。

**排查**：日志里有两条关键信息——流水线以 **1 fps** 启动（配置是 30fps，
自适应帧率把它压下来了），紧接着 ``llama-server 推理失败 ... TimeoutError``。
列出 ``llama-server.exe`` 进程发现 **8 个**，合计 **23.3 GB** 内存：

.. code-block:: text

    893 MB / 3812 MB / 2325 MB / 4519 MB
    1201 MB / 5762 MB / 1458 MB / 4424 MB

**成因**：``llama-server`` 是本程序拉起的独立子进程（见 2.11）。正常退出时
程序会逐个终止它们，但如果是**被强制结束**的——任务管理器"结束任务"、
崩溃、断电——清理代码根本没有机会执行，子进程就变成孤儿活了下来。
每强杀一次泄漏两个（两个模型各一个），反复几次就把整机拖垮：
内存被占满、显存被挤到使用共享内存（走 PCIe），推理因此慢到超时。
**"GPU 99%"是假象**——它确实在忙，忙着在内存与显存之间来回搬数据。

**修复（两层）**

1. **内核级保障**：用 Windows **作业对象**（Job Object）把子进程绑到父进程上，
   设置 ``JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE``。父进程无论正常退出、崩溃还是
   被强杀，内核关闭其句柄后作业对象随之销毁，其中的进程被**内核直接终止**——
   不依赖我们写任何清理代码。实现在 :mod:`pingyitong.utils.process_guard`，
   在 ``_spawn()`` 里对每个子进程调用 ``assign_to_job()``。
2. **给已被弄脏的机器收尸**：启动时清理上一次遗留的孤儿进程
   （``reap_stale_servers``）。判据是"可执行文件位于本程序运行时目录"，
   仅按进程名匹配是不够的——用户可能自己也在用 llama.cpp。
   这一步**必须在启动任何推理进程之前同步执行**：判据同样适用于我们自己
   刚拉起的进程，放到后台线程里跑就可能误杀自己。

**为什么不能只靠"好好写清理代码"**：程序被强杀时没有任何 Python 代码会执行
（信号处理、``atexit``、``finally`` 都不会跑）。这类资源归属问题必须交给
操作系统兜底。

**验证**

- ``scripts/verify_child_cleanup.py``：起一个父进程、在作业对象里拉子进程、
  用 ``taskkill /F`` 强杀父进程，检查子进程是否消失。修复后子进程立即消失。
- 真机实测：程序运行时 2 个推理进程 → ``taskkill /F`` → **残留 0 个**，
  内存回落到 39.9%；修复前同样操作每次泄漏 2 个。
- ``tests/test_process_guard.py`` 还锁定"未加入作业的进程不受影响"
  与"同名但不在本程序目录下的进程不得被清理"两条防误伤性质。

### 6.9 翻译层的呈现：背景过大与逐帧闪烁

用户反馈"**字幕出现的动态效果太差了，根本没法看**"和
"**字体显示的背景黑框范围过大**"。两处都在渲染层，原因彼此独立。

**背景黑框过大**：背景遮罩直接按 ``item.box``（**原文**包围盒）绘制。
中英互译的字符数差一倍以上，于是一句短译文被一个沿用原文宽度的黑框包住。
实测：原文包围盒 900px 宽，译文"打开设置面板"只有 6 个字，
背景却是 900px —— 收缩后 186px，减少 79%。

改法是背景按**译文实际占用的范围**收缩：在 :class:`TextLayout` 上记录
实测的最长行宽（:func:`~pingyitong.components.render.layout.measure_lines`
用 ``QFontMetricsF`` 量取，而不是按字符数估算——中英混排估算误差很大），
背景取"最长行宽 + 内边距"与"总行高 + 内边距"，左上角与文字对齐。
文字位置不变，因此译文不会因为背景收缩而移动。

**逐帧闪烁**：画面差分只把"变化的区域"送去识别，增量帧里的条目因此只覆盖
屏幕的一小块。而渲染层原先**无条件替换整层内容**：

.. code-block:: python

    for name, window in self._windows.items():
        window.set_items(buckets.get(name, []))   # 一律替换

于是每一帧，未变化位置的译文都被清空、下一帧再画回来 —— 屏幕上大部分文字
在每秒十余次的刷新里不断消失又出现，完全无法阅读。这也让延迟在观感上
被放大：内容其实早就翻译好了，只是不停地闪。

改法是把"整帧"与"增量帧"区分开（``RenderFrame.is_full_frame`` 已经区分了，
只是没传到渲染层）：

- **整帧识别**：替换整层内容（文字消失时应当清空）；
- **增量帧**：只替换与本次识别区域**几何相交**的旧条目，其余保持不动；
  没有新条目的窗口也不清空。

回归测试见 ``tests/test_design_system.py::TestOverlayPresentation``，
覆盖"背景贴合短译文""背景不超出可用区域""增量帧保留未变化条目"
"增量空帧不清空""整帧仍整体替换"五条性质。

**关于延迟**：实测各阶段耗时为「捕获 + OCR 1.44s，1.7B 翻译 1.00s，
4B 翻译 1.74s」（框选区域 1629×1305）。OCR 是最大单项，且已经是调优后的
结果（``use_cls=False``、线程数上限 8）。可控的部分是模型调度：
配置里残留的 ``auto`` 模式会在长句时切到 4B（慢 74%）并可能触发重载，
与"实时"目标相悖，因此恢复为与 schema 默认一致的
``manual + 1.7B + content_adaptive=False``。

### 6.10 实时译文文本框与阅读顺序（自研）

**需求**：悬浮栏新增向下箭头，点击在下方展开文本框，译文实时显示其中，
文字按界面"从上到下、从左到右"的顺序排列以保证语义流畅；
另提供"语义精简"开关。

**关于实现来源**：调研过 GitHub 上的现成方案，均不适合本项目，
三个功能均按经典算法与项目既有设施自行实现：

- 阅读顺序：``axa-group/Parsr``（Apache-2.0）的 ReadingOrderDetectionModule
  是 TypeScript 独立服务、要跑 Docker；``layoutreader`` 需要 ``transformers``
  与约 500MB 模型；``kraken`` 是完整 OCR 引擎、与项目已有的 RapidOCR 重复。
  故按经典 **XY-cut** 版面分析思路自研
  （:mod:`pingyitong.services.reading_order`）。
- 折叠面板：``bec_widgets`` 的 ``CollapsiblePanelManager`` 依赖其自有控件
  框架，视觉与项目设计令牌不符；故用项目既有动效设施自研
  （:class:`~pingyitong.ui.widgets.transcript_panel.TranscriptPanel`）。
- 语义精简：社区只有提示词**文本示例**，无可安装组件；故在自研 Prompt
  工程中加入 ``CONCISE MODE`` 规则块。

**因为不是取自 GitHub 的组件，需求文档（PPT/Word）无需新增来源标注。**

**阅读顺序为什么不能按 (y, x) 直接排序**：屏幕同时开着侧边栏与主内容区时，
同一水平带上的元素分属不同区域，按 y 排会让两边内容交替出现
（"设置 / The quick brown fox / 历史 / jumps over…"），读起来支离破碎。
XY-cut 先找"竖切"分栏（空隙需达中位行高的 1.4 倍，避免把词间空隙误判为
栏间距），栏内按行带分组、行内从左到右。

**文本框与原位渲染共用一份增量合并规则**：文本框要显示"当前屏幕的全部
译文"，而增量帧只含变化区域，因此流水线维护合并快照——合并规则调用与
渲染层相同的 :func:`merge_items`，保证两处内容一致。

**展开动画的两个 Qt 坑**（都有回归测试）：

1. 只动画 ``maximumHeight`` 面板不会长出来——它只是"允许"长到目标高度，
   实际高度仍由布局的 sizeHint 决定。必须把高度包装成可动画的 Qt 属性
   （``pyqtProperty``）真正改尺寸；测试断言**动画中途**高度处于 0 与目标
   之间，防止"点一下没反应、然后突然出现一整块"。
2. 半透明无框窗口会禁用顶层窗口的自动背景填充，而 :class:`QFrame` 的
   默认 ``paintEvent`` 在 Qt 6.11 下不代绘样式表背景——实测面板完全透明、
   只剩文字浮在桌面上。标准解法是在 ``paintEvent`` 中主动绘制
   ``PE_Widget``。

**语义精简的边界写进提示词**：只压缩措辞（客套、冗余代词、重复限定），
禁止省略或改写专业/学术术语、专有名词、品牌名、数字、单位与代码标识符，
并保留否定、条件、数量、比较——否则"更短"会变成"更错"。

### 6.11 翻译延迟的实测结论与配置深合并缺陷

用户反馈"模型翻译速度还是太慢"，并给出 vLLM/量化/上下文三项建议。
逐项实测后，结论如下（**以测量为准，不以推断为准**）：

**已到位的部分**

- 量化：两个模型**本来就是 Q4_K_M**（``models/Spark-X2.5-{1.7B,4B}-Q4_K_M.gguf``）；
- 分进程部署：1.7B 与 4B **本来就是两个独立 ``llama-server`` 进程、各自随机端口**，
  显存互不抢占——建议中的这一条早已是现状；
- 上下文：4B 由 4096 降到 **2048**（一次批量请求实测约 1000 token，足够），
  KV 显存减半。

**实测无效或不适用的部分**

- **vLLM 不可用，且不是不努力**：``spark2_5`` 架构目前只有 XHToken 的
  llama.cpp 分支支持，vLLM 的模型注册表没有这个架构，加载即失败；
  且 vLLM 无原生 Windows 支持。至于连续批处理的吞吐收益——本项目每帧
  已把多段合并成**一个请求**（单客户端），批处理收益不适用于该负载。
- **FlashAttention（``-fa on``）与 KV 复用（``--cache-reuse 256``）**：
  1.7B 上实测中位延迟 0.95s → 0.93s（噪声级）。原因：该负载是
  **生成受限**（182 个输出 token 主导耗时），预填充占比很小。
  二者对 4B 与更长提示有益无害，已固定开启。
- **KV 缓存量化（q8_0）**：实测无收益且首次请求变慢（11.75s），
  未采用。
- **CUDA 后端**：运行时目录虽有 ``ggml-cuda.dll``，但 CUDA 12.4 构建不含
  RTX 50 系（Blackwell，sm_120）的内核，发布方文档明确建议 50 系改用
  Vulkan。Vulkan 是本机唯一可行的 GPU 后端。
- **设备选择**：``--list-devices`` 显示 NVIDIA + Intel 核显两块 Vulkan 设备，
  实测指定 ``--device Vulkan0`` 与默认无差异（未发生跨设备层拆分）。

**本机真实速度上限**：1.7B Q4_K_M 在 Vulkan 上生成 ≈ **190 tok/s**，
12 段批量翻译 ≈ 0.95s；增量帧 OCR ≈ 0.45s。新内容端到端 ≈ 1.2–1.4s，
未变化内容全部命中翻译缓存（≈0ms）。生成时间与输出 token 数成正比，
因此**语义精简开关（压缩输出）是用户侧最直接的提速手段**。

**顺带发现并修复的真实缺陷：配置深合并**。为把 4B 上下文写入配置而做
局部补丁时，``merge_into`` 只合并一层——
``{"model": {"accurate": {"n_ctx": 2048}}}`` 把整个 ``accurate`` 子节
替换成单字段字典，模型文件名回落为空、高精度模型"消失"。
修复为递归深合并（只覆盖补丁里出现的字段），并加回归测试锁住
"两级补丁不得重置同节兄弟字段"。

### 6.12 文本框模式的三个连锁缺陷

用户反馈"**开启文本框翻译模式后，并没有进行翻译**"与"**翻译的语言不准确**"。
排查发现三个问题连锁：

**一、渲染入口被短路。** ``_render_tick`` 第一行是"翻译层不可见直接返回"，
而文本框模式恰恰要隐藏翻译层——渲染阶段整体短路，``_update_transcript``
永远执行不到。翻译线程一直在正常产出，结果全部在结果队列里被当作过期帧
丢弃。修复：两个消费方（翻译层 / 文本框）各自判断可见性，翻译层隐藏时
只跳过绘制，不跳过分发。

**二、流水线未运行。** 文本框展开时若流水线停着，面板只会永远停在
"等待识别"。现在展开即自动开始翻译（收起不自动暂停）。

**三、OCR 自我反馈污染。** 悬浮栏与文本框显示在被捕获的屏幕上，它们的
文字会被 OCR → 翻译 → 再显示。文本框是 35% 半透明的，面板文字与背后的
屏幕内容**叠加**后 OCR 读出"板，开算成的识另真机"式的混合乱码。
修复是把这些窗口的几何（物理坐标）作为忽略区传给流水线，落在其中的
识别结果一律丢弃。这里有一个隐蔽的时序坑：推送发生在展开动画**开始时**，
此刻 ``height()`` 还在从 0 长大——按瞬时高度推送，面板 90% 的区域脱离
忽略区。修复是推送"目标高度"矩形（:attr:`ignorable_rect`），
与动画进度无关。

**"翻译语言不准确"的另两个来源与修复**

- 命令行 / 代码片段被送进模型：``cd "F:/讯飞" && cat > /tmp/x <<EOF``
  这类内容的"译文"基本是乱码，而提示词本就要求技术 token 原样保留——
  既然正确结果就是"不翻"，在送模型前识别出来直接跳过
  （:mod:`pingyitong.services.code_filter`，启发式规则、宁可漏判不可误判）。
  实测一屏 16 段中 5 段命令行全部正确跳过。
- 提示词缺少输出语言的硬约束：新增规则
  "Write the ENTIRE translation in <target>（唯一例外是原样保留的技术
  token）"，压制"半翻译"的混合语言输出。

### 6.13 打包交付链路：OCR 依赖、自检与 OCR 延迟的第二轮实测

**一、安装包版本"OCR 组件不可用"。** 用户在**安装后的程序**里开启实时翻译，
报"OCR 组件不可用: No module named 'rapidocr'"。开发环境完全正常——
这是典型的打包问题，逐层排查：

1. `--hidden-import rapidocr_onnxruntime` 只会导入模块本身，不会带上
   RapidOCR 的**数据文件**（三个 ONNX 模型）与**动态子模块**——改用
   `--collect-all rapidocr_onnxruntime`（同理覆盖 trafilatura、
   charset_normalizer）；
2. 仍然失败：AST 分析 RapidOCR 的顶层 import 发现它硬依赖 `PIL`，
   而 `PIL` 恰好在打包脚本的 `excludes` 清单里——从排除清单移除
   `PIL`（以及依赖链上的 setuptools/pkg_resources/distutils）后修复。

**二、`--self-check` 安装自检。** "import 成功"不等于"能识别"：ONNX 模型
文件没打进去时 import 照常成功、`is_ready()` 返回 True，一识别就报错。
新增 `PingYiTong.exe --self-check`：对合成图像做**一次真实 OCR 推理**
（必须读出文字才算通过）、按最小尺寸实抓一帧屏幕、核对两个 GGUF 权重、
探测 llama-server、验证数据目录可写。两个实现坑：

- 独立进程里 `QGuiApplication.screens()` 在**没有应用实例**时返回空列表，
  会把"没建应用"误报成"没有显示器"——自检必须自建 Qt 实例并持有引用
  （局部变量一析构，C++ 实例随之销毁）；
- 打包产物是窗口子系统，没有控制台，`print` 的结果用户看不见——
  报告改为弹窗展示（`QApplication` 必须先于 `QGuiApplication` 建立，
  顺序反了会抛 RuntimeError 弹不出窗），同时写入
  `%LOCALAPPDATA%\PingYiTong\selfcheck.log`。

**三、端到端延迟：第二轮实测（基准脚本重写 + 三个 OCR 瓶颈）。**
旧基准把"屏幕当前显示的内容"当输入、跑完一圈却不核对识别出了什么，
报出的"78ms"是空转数字。重写为 `scripts/bench_real_e2e.py`：
把**已知英文台词**渲染成字幕画面 → 真实 OCR → 真实模型 → 逐条核对译文，
缓存全部关闭。三个实测修复：

1. **检测补边**（78→46ms）：RapidOCR 默认把宽高比 > 8 的图**上下补边**到
   `max(宽/8, 30)×2` 高，字幕条 1600×84 被补成 1600×400，检测面积膨胀
   4.7 倍。`width_height_ratio` 设大值关闭。
2. **检测降采样**（46→16ms）：检测耗时与像素数成正比，检测在长边 800px
   的降采样图上做，识别框按比例映射回原图**从原图裁剪**——识别精度
   不受影响（识别输入固定缩放到高 48px）。降采样后一个框都检不出时
   退回原尺寸再检一次。
3. **宽行毒化识别批次**（实机整屏 OCR 4.3s → 1.3s）：`text_rec` 把整批
   识别输入补边到**批内最大长宽比**——混入一个 ratio≈60 的整行代码块，
   同批 5 个普通块从 36ms 拖到 887ms。超过 ratio 20 的裁剪块按"空白列"
   切成 ratio ≤ 16 的段再识别、结果拼接（切点必须落在 ≥ 行高 18% 的
   空白段上才算词间空格，否则按硬切处理直接相连——仅按 ink≈0 判定会把
   字距间隙误判成空格，拼出 "th e"）。实测拆 4 段与整块识别结果逐字一致。
   另回退了此前"固定 rec 输入宽 1344"的做法：`resize_norm_img` 把整批
   补到 `max(基准比, 批内最大比)`，基准比 28 意味着每一批都按最宽算，
   普通批成本翻倍。

**实机测量存档**（`docs/measurements/`，缓存关闭、逐条核对译文）：

| 场景 | 1.7B | 4B |
| --- | --- | --- |
| 1 行字幕 e2e p95 | **188ms** | **141ms** |
| 2 行字幕 e2e p95 | **297ms** | **219ms** |
| 4 / 8 行密排文本 | 531 / 1453ms | 391 / 734ms |

300ms 门槛按规格定义适用于**标准字幕场景（1–2 行）**：两个模型均通过。
4 行以上的密排文本物理上受输出 token 数限制，如实标注、不谎报达标。
安装后程序的实测（受控字幕换行）：稳态端到端 **94–300ms**；新行首次
出现 ~514ms（冷识别）；整屏滚动终端这类最坏场景 OCR 1.3–2.5s（切段前
为 2.5–4.3s）。

### 6.17 源语言 OCR 路由与完整方向审查（0.6.13）

### 6.18 组合附标的代码误判与子进程归属（0.6.14）

实测五种 Indic 源图在 1420 行中被误判为代码，源/目标不同的 1410 行因此未调用模型。
代码过滤器现在将紧随词字符的 Unicode 组合附标作为拼写的一部分；附标从符号计数与
分母同时排除，避免堆叠附标稀释真实代码符号比例。未附着的附标仍按符号处理，
命令语法、路径、选项与技术文本的保留逻辑不变。五源×142目标×两模型另行进行真实增量复跑。

启动清理仅处理本应用登记的推理子进程，核对 PID、创建时间、完整 exe 路径和启动者身份。
活启动者、未登记的用户服务、权限或身份不明者保留；旧版本未登记的孤儿不凭目录猜归属。
Win32 作业对象句柄使用指针宽度 ABI，父进程结束时由内核释放其推理子进程。
受控真实回归仅创建并清理测试自己的进程，验证活服务保留及已退出启动者的孤儿被回收。

0.6.14 完整生产回归 **1044 项、66.621 秒，OK，退出码 0**。该版本未加入语言身份分类器，
同脚本冷门语言的模型错误和 OCR 缺失仍是已知限制，完整 0.6.13 基准不会被改写为新版全量通过。

## 八、与需求文档的差异汇总

诚实记录实现与《项目全栈开发文档》《产品功能规划》的差异：

| 文档描述 | 实际实现 | 原因 |
| --- | --- | --- |
| 多进程 + 队列 | 多线程 + 队列 | 见 2.1：多进程与"8GB 可运行"目标冲突 |
| PyQt6 提供透明窗口 | 同左 | — |
| llama.cpp 作为推理引擎 | 同左，**双后端**：外部 `llama-server` 进程（默认）或 llama-cpp-python 进程内 | 见 2.11：Spark-X2.5 的 `spark2_5` 架构只有 XHToken 的 llama.cpp 分支支持，上游 llama.cpp 不支持，故 llama-cpp-python 无法加载权重 |
| — | 增加"预览模式" | 模型未就绪时仍可验证渲染链路，且如实标注 |
| — | 增加 `LayoutPreviewEngine` | 同上 |
| "支持 200+ 种语言" | 142 种语言可选；111/26/5 为历史固定句试译分档 | 输出脚本检查不能证明语言身份、语义、OCR 或全部方向可用；0.6.13 全部组合已审查，包含失败，0.6.14 对受影响方向增量复跑 |
| 首期 8 种语言 | 142 种（1.7B 与 4B 分别实测） | 8 种远小于模型实际能力，限制用户可选范围没有依据 |

其余需求（差异化捕获、双模型调度、原位渲染、术语库、历史记录、
热键、多屏与高 DPI、样式自定义）均已实现，见对应模块与测试。

### 3.4 性能优化点（按收益排序）

1. **OCR 线程数调优**：整屏 5.89 s → 0.97 s（6 倍）。见 3.3 节；
2. **画面差分**：静态界面完全不触发 OCR 与推理；增量帧只处理变化区域，
   单帧 OCR 降到 0.31 s；
3. **预热**：把十几秒的首次推理与数秒的 ONNX 初始化移出用户交互路径；
4. **推理缓存**：界面文字高度重复（菜单、按钮、状态栏），实测第二次
   相同内容全部命中，耗时 0 ms；
5. **批量推理**：短片段合并请求，摊薄固定开销；
6. **渲染限制**：只绘制视口内条目；排版结果按
   `(文本, 宽, 高, 样式版本)` 缓存。
