# 屏译通

**基于本地大模型的桌面实时原位翻译系统**

屏幕所见即所译 —— 实时捕获桌面画面、本地 OCR 识别、本地大模型翻译，
译文以**原位叠加**方式显示在原文所在位置，实现"沉浸式对照阅读"。

默认使用本地识别与翻译。启用「在线 AI」后，待翻译文字会发送到你配置的服务；
启用联网预翻译也会访问相关内容来源。应用不设置遥测。

## 核心特性

| 特性 | 说明 |
| --- | --- |
| **全域实时翻译** | 后台按 15fps（可调）监控桌面，画面差分只处理变化区域，无需手动截图或框选 |
| **原文坐标原位渲染** | 译文按原文包围盒绘制在屏幕最上层的透明窗口上，鼠标穿透、不影响正常操作 |
| **两种显示模式** | 完全覆盖（遮住原文）与半透明叠加（便于中英对照），一键切换 |
| **双本地模型驱动** | Spark-X2.5-1.7B 极速 / 4B 高精度，手动切换或自动调度 |
| **在线 AI 接入（可选）** | 填入任意 OpenAI 兼容服务的 API Key（DeepSeek、智谱、Kimi、通义、OpenAI、本机 Ollama 等），翻译改由云端大模型承担：质量更高、批量并发更快；断网或调用失败自动回退本地模型 |
| **三级智能调度** | 手动模式 → 资源自适应 → 内容自适应；负载过高自动降级保护交互流畅度 |
| **多语言互译** | 142 种语言可选；自动识别适合中、英、日及繁体，其他源语言需手动指定。可选清单与历史试译标记不保证 OCR 或每个翻译方向可用（见下文） |
| **全离线运行** | 断网环境下功能完整可用，翻译历史仅保存在本机 |
| **自定义翻译区域** | 框选屏幕局部区域翻译，降低占用并避免误翻译无关窗口；区域会按显示器缩放比例精确换算 |
| **全局热键** | 任意应用中均可开关翻译、切换模型、复制译文、隐藏翻译层 |
| **翻译样式自定义** | 字体、字号、颜色、遮罩透明度、圆角、阴影、最大行数，带实时预览 |
| **专业术语库** | 随安装包预装软件与 AI 多语言词库，可随时切换客户 CSV，保证术语翻译一致 |
| **实时译文文本框** | 悬浮栏点击 ▾ 展开与悬浮栏等宽的文本框（35% 半透明底），译文按屏幕阅读顺序（先分栏、再按行）实时汇总呈现，可选中复制 |
| **语义精简** | 可选开关：压缩措辞而不改变语义，专业术语、数字、单位与代码标识符一律不省 |
| **翻译历史回溯** | 本地 SQLite 存储，支持关键词检索与 TXT/CSV 导出 |
| **多显示器与高 DPI** | 每块屏幕独立翻译层，150%/200% 缩放下坐标精确对齐 |

## 快速开始

### 环境要求

- Windows 10 / 11（x86_64）
- Python 3.10 或更高版本（已在 **Python 3.11.9** 上完整验证）
- 最低配置：4 核 CPU、8GB 内存、集成显卡
- 推荐配置：6 核以上 CPU、16GB 内存、独立显卡（有 GPU 后端可自动加速）

### 安装

```bash
# 1. 安装依赖
#    llama-cpp-python 建议从预编译 wheel 索引安装，避免本地编译
#    （Windows 上从源码编译需要 MSVC 工具链）
python -m pip install -r requirements.txt ^
    --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpu

# 2. 安装本项目（可选，装上后可用 pingyitong 命令启动）
python -m pip install -e .

# 3. 启动
python run.py
```

> 国内网络环境可加 `-i https://pypi.tuna.tsinghua.edu.cn/simple` 加速。

首次启动后程序会最小化到系统托盘，双击托盘图标或右键选择"设置…"打开主面板。
**模型会在启动时自动加载并预热**（1.7B 约 3 秒 + 预热数秒），期间界面正常可用。

### 便携模式

把配置、日志、历史数据库与模型目录全部放在程序目录下，不在系统盘留痕：

```bash
python run.py --portable
```

### 自定义数据目录

```bash
python run.py --home D:\PingYiTongData
```

## 模型准备

本项目**已随交付目录包含** Spark-X2.5 的 GGUF 量化权重（位于 `models/`）
与推理运行时（位于 `runtime/llama/`），启动即自动加载，无需任何配置。

### 权重清单

| 文件 | 大小 | 用途 | 启动时加载 |
| --- | --- | --- | --- |
| `Spark-X2.5-1.7B-Q4_K_M.gguf` | 1.03 GB | 极速模式 | ✅ 自动加载 + 预热 |
| `Spark-X2.5-4B-Q4_K_M.gguf` | 2.42 GB | 高精度模式 | 首次使用时按需加载 |

来源：Hugging Face `XHToken/Spark-X2.5-1.7B-GGUF` 与
`XHToken/Spark-X2.5-4B-GGUF`（**Apache-2.0**）。

> **关于来源的一处更正**：项目立项文档中标注的权重仓库为
> `iflytek/spark-llm`。经核实该仓库当前不存在（返回 404）；
> 实际公开发布 Spark-X2.5 系列的是 XHToken。本项目按实际来源引用。

### ⚠️ 必须使用 llama-server 后端（重要）

Spark-X2.5 的模型架构是 `spark2_5`，**只有 XHToken 维护的 llama.cpp 分支
支持它**。上游 `ggml-org/llama.cpp` 不认识该架构，而 `llama-cpp-python`
捆绑的正是上游版本，因此它**无法加载 Spark-X2.5**：

```
llama_model_load: error loading model: unknown model architecture: 'spark2_5'
```

这不是版本新旧的问题——架构支持只存在于分支里，换任何版本都无效。

因此程序**首选 `llama-server` 外部进程后端**（自动探测，无需配置）：

```
runtime/llama/llama-server.exe   ← 由 XHToken/llama.cpp 分支构建
      ↑ 程序自动拉起该子进程并通过本机回环地址(127.0.0.1)通信
```

`llama-cpp-python` 仍然保留，用于架构受上游支持的其它 GGUF 模型。
后端选择是自动的，详见 `components/llm/backend.py`。

### 推理运行时

| 项目 | 说明 |
| --- | --- |
| 位置 | `runtime/llama/`（约 596 MB，含 CPU / CUDA 12.4 / Vulkan 三种后端） |
| 来源 | 社区从 `XHToken/llama.cpp` 分支构建的 Windows x64 版本 |
| 下载 | `python scripts/download_runtime.py` |
| 查询位置 | `python scripts/download_runtime.py --show-paths` |
| 校验 | `python scripts/download_runtime.py --verify-only` |

**GPU 加速**：程序启动时自动检测 GPU 后端并把全部层卸载到显卡。本机实测
的 RTX 5070 Ti 走 **Vulkan** 后端（CUDA 12.4 不支持 Blackwell 架构的
sm_120 计算能力，因此 CUDA 后端在这张卡上不可用，Vulkan 可以）。
用 `llama-server.exe --list-devices` 可查看可用设备。

### 为什么 4B 默认不预加载

高精度模型占用约 2.8GB 内存。在 8GB 内存的机器上同时常驻两个模型会与系统
和其他软件争抢内存，整体反而更慢。因此策略是：

- **1.7B 常驻**——启动即加载**并预热**，保证任何时候都能立即响应；
- **4B 按需**——首次需要时加载，空闲 180 秒后自动卸载释放内存。

**预热**很关键：模型加载完只是把权重读进内存，第一次真正的前向计算仍要
付出可观开销（实测首次翻译 11–21 秒，之后每句 0.06–0.11 秒）。预热把
这笔开销提前到启动阶段，用户点"开始翻译"时就是立即可用的。

内存充足（16GB 以上）时，可在设置面板的「模型」分页开启 4B 的预加载。

### 两个实测踩到的坑（都已处理）

**1. GGUF 权重不含 chat template。**
`tokenizer.chat_template` 在权重里是缺失的，直接走补全接口会让模型看到
裸文本，输出退化成 `"As As As As…"` 这类重复片段。程序使用随附的官方
模板（`assets/chat_templates/spark-x2.5.jinja`）并走对话接口。

**2. 推理模型默认会先"思考"。**
Spark-X2.5 默认先输出思考过程，实测同一句话：关闭思考约 0.1 秒、
开启约 0.6 秒。桌面实时翻译需要即时响应，因此**默认关闭思考**。
开启后措辞可能更贴切（例如 "Save As" 关闭时译"保存为"、开启时译
"另存为"，后者才是 Windows 菜单的标准译法），可在配置文件中把
`model.enable_thinking` 设为 `true`。

### 权重丢失或需要重新下载

若从版本库克隆（权重与运行时被 `.gitignore` 排除），依次运行：

```bash
python scripts/download_runtime.py               # 推理运行时（约 245 MB）
python scripts/download_models.py                # 两个模型（约 3.45 GB）
python scripts/download_models.py --model 1.7b   # 只要极速模型（约 1.03 GB）
```

两个脚本都**只依赖标准库**（无需先 `pip install`）、支持**断点续传**、
**自动切换可用镜像**（`huggingface.co` 与 GitHub Release 在国内多数网络下
不可直达）。

### 权重也可以手动放置

程序会在以下位置依次查找，**先找到的优先**：

| 顺序 | 位置 | 适用场景 |
| --- | --- | --- |
| 1 | `$PINGYITONG_MODELS_DIR` | 自定义位置（环境变量） |
| 2 | `<项目目录>/models/` | 源码运行（默认下载到此） |
| 3 | `%LOCALAPPDATA%\PingYiTong\models\` | 便携模式或安装后的数据目录 |

**文件名不必完全一致**：程序先精确匹配，再大小写不敏感匹配，
最后按参数量特征（`1.7b` / `4b`）模糊匹配。因此从 Ollama 或 LM Studio
下载的文件也能被正确识别。

### 未准备权重时会怎样

程序**不会崩溃也不会静默失败**，而是进入**预览模式**：

- 译文的位置、字号、换行、多屏适配等**渲染链路全部正常工作**；
- 译文内容为 `〔未加载模型〕原文` 占位标记；
- 界面顶部状态条、托盘提示与通知都会明确标注当前处于预览模式。

**程序不会把占位内容伪装成翻译结果。**

## 使用说明

### 基本流程

1. 启动程序 → 托盘出现图标；
2. 打开设置面板 → 「常规」分页选择**目标语言**；
3. 点击 **开始翻译**（或按 `Ctrl+Alt+T`）；
4. 阅读屏幕上的外文内容 —— 译文会直接出现在原文位置。

### 在线 AI 模型（可选）

设置面板「模型」页的**在线 AI 模型**卡支持接入任何 OpenAI 兼容服务：
选服务商预设（或选「自定义」）→ 填接口地址、API Key、模型名 →
点**测试连接** → 打开开关。

- **工作方式**：翻译请求优先路由到云端模型，术语库、批量对位、
  阅读语序还原等上游链路完全复用；云端失败（断网、Key 失效、限流）时
  该次请求**自动回退本地模型**，连续失败 3 次进入 60 秒冷却期，
  期间直接走本地，不再白付超时。认证/权限/地址/请求被拒类错误
  （400/401/403/404，其中 400 最常见于模型名写错）重试必然复现，
  首次失败即进入冷却——同一帧的后续片段不必再逐段白付往返。
  其中点名参数的 400（如 OpenAI 推理系要求 `max_completion_tokens`、
  部分模型只接受默认温度）会按错误提示自适应改参并当次重试，
  两处怪癖同现（o 系/gpt-5 既不收 `max_tokens` 也不收自定义温度）
  也在同一次请求内学完；学习一次后直接按正确参数发出，不会因此进冷却；
  「测试连接」成功也会立即解除冷却。响应被输出上限截断
  （`finish_reason=length`）时自动按翻倍预算重问一次，仍不完整则按失败
  回退本地——半截译文不会画上屏幕。帧内发生回退时，该帧结果不入
  推理缓存（防止本地回退结果被后续在线帧误命中），但复制、历史与
  状态统计照常记录这一帧，与屏幕显示保持一致。
- **速度**：在线模式按「在线批量段数」（默认 10）与「并发请求数」
  （默认 4）把整帧拆批并发发送，整帧延迟约降为 1/N；引擎复用
  TCP/TLS 连接，省去每次握手的 100–300ms——启用开关时即按并发数后台
  并行预建连接（整帧多批的首帧也不付握手），首个请求直接复用现成连接，
  TLS 上下文全引擎只建一次
  （新建连接不再重复加载系统证书）；批量对位失败降级逐条重试时，
  在线模式同样并发发送（本地模式保持串行）。短句场景本地 1.7B 仍是
  绝对延迟最低的选择，在线模式的优势在翻译质量、长上下文，
  以及无 GPU 机器上可用的"高精度速度"。
- **隐私**：API Key 明文保存在本机配置文件，仅随翻译请求发送给你
  填写的服务商；屏幕内容会作为翻译输入上传给该服务商——
  介意者请保持关闭（程序默认关闭）。

### 语言支持实测

模型官方只给出了一句总体声明 —— "support for more than 200 languages"，
**没有公布这 200+ 种语言的具体清单**（已核对模型仓库 README 与 config.json）。

以下是旧版固定探针句对 **142 种目标语言**的历史试译分档，主要检查输出文字脚本。
同一脚本对应多种语言，因此这些分档不能证明目标语言身份、语义准确度、
源语言 OCR 或全部源×目标组合可用。

| 档位 | 数量 | 含义 | 界面标记 |
| --- | --- | --- | --- |
| 历史双模型通过 | **111** | 两个模型均满足旧固定句判据 | `✓` |
| 历史疑似 | **26** | 仅一个模型通过，或仍需进一步核查 | `~` |
| 历史未通过 | **5** | 两个模型均未通过该固定句判据 | `✗` |

旧探针中 4B 通过 133 项、1.7B 通过 115 项；两者结果不完全包含。
这些数量只描述旧探针，不是语言准确度认证。

设置面板的语言下拉框会把这三种标记直接标在选项上，并支持按中文名、英文名或
母语名搜索（例如输入 `冰岛`、`Icelandic`、`日本語` 都能定位）。0.6.13 增加了
按手动源语言选择离线 OCR 的处理，缺少对应模型会明确提示。
全部组合审查的进度与已知边界见 [功能审查记录](docs/measurements/language_functional_audit_20261006.md)。

复现方式：

```bash
python scripts/test_languages.py --model 1.7b --output docs/language_test_1.7b.json
python scripts/test_languages.py --model 4b   --output docs/language_test_4b.json
```

原始记录见 `docs/language_test_1.7b.json` 与 `docs/language_test_4b.json`；
测试 `tests/test_language_results.py` 会校验代码中记录的结果与这两份原始记录
完全一致，避免人工抄写走样。

### 双模型怎么选

- **极速 1.7B**：内存占用低、响应快。适合短句、常用词汇、日常界面文字，
  以及低配笔记本。
- **高精度 4B**：长句、复杂句式、专业术语处理更准确。适合阅读技术文档、
  学术论文、专业软件界面。
- **自动调度**（默认）：由程序根据 CPU 负载、GPU 显存空闲与文本复杂度
  自动选择，两者兼顾。

自动调度的保护机制：CPU 持续高于 70% 或渲染帧率低于 10fps 时自动降到
1.7B 保证桌面流畅；且两次切换之间至少有 8 秒冷却，避免模型反复加载卸载。

### 术语库

安装后默认启用[预装多领域术语库](config/glossaries/README.md)中的「软件与 AI」。术语库覆盖双模型实测确认的 137 种语言：软件与 AI 34 个概念，另有医疗、生物、历史、物理、化学、数学 136 个概念。只有存在明确本地化名称的语言对才使用该译名；没有译名时不猜译。客户可在「术语库」分页选择预装领域，或导入 CSV 并随时切换：

```csv
原文,译文
machine learning,机器学习
Spark-X2.5,讯飞星火 X2.5
```

第三列可指定是否区分大小写，第四列指定是否整词匹配（填「是」或「否」）；可选第五、六列限定源语言和目标语言，不填则对所有语言方向生效。
参考 [`config/glossary_sample.csv`](config/glossary_sample.csv)。

术语在翻译前会被替换为不可见的占位符，翻译后还原，因此不会因上下文变化
而被模型改写；即使模型漏抄占位符，程序也能检测并清除，不会在屏幕上留下乱码。

## 技术架构

### 五层分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ UI 交互层                                                     │
│   系统托盘 · 主设置面板 · 悬浮控制条 · 原位翻译透明层          │
├──────────────────────────────────────────────────────────────┤
│ 业务功能层                                                    │
│   实时翻译 · 区域翻译 · 热键管理 · 术语库 · 历史记录           │
├──────────────────────────────────────────────────────────────┤
│ 核心调度层                                                    │
│   流水线调度 · 双模型调度 · 资源监控 · 坐标映射                │
├──────────────────────────────────────────────────────────────┤
│ 基础组件层                                                    │
│   屏幕捕获 · OCR · 图像处理 · 大模型推理 · 窗口渲染            │
├──────────────────────────────────────────────────────────────┤
│ 硬件层                                                        │
│   CPU · GPU · 内存 · 显示器（多屏 / 高 DPI）                   │
└──────────────────────────────────────────────────────────────┘
```

层间通过明确定义的接口通信，可独立开发、独立测试、独立替换。
**上层可以调用下层，下层绝不反向依赖上层**——除渲染层因为需要 Qt 事件循环
而与 UI 层有所耦合外，业务逻辑与核心算法完全不依赖 Qt。

### 异步流水线

```
捕获线程        捕获桌面画面 ──┐
                              │  LatestQueue（容量 2，丢旧保新）
OCR 线程        文字识别 ─────┤
                              │  LatestQueue（容量 3）
翻译线程        预处理+推理 ──┤
                              │  LatestQueue（容量 3，仅保留最新）
主线程渲染      原位叠加绘制 ─┘  ← QTimer 驱动，必须在主线程
```

**背压策略：丢弃最旧数据，而不是阻塞上游。**
屏幕翻译场景下时效性远重于完整性：延迟 2 秒的译文即使准确也没有价值，
而且会覆盖掉更准确的新结果。

> **与开发文档的实现差异说明**
>
> 开发文档描述为"多进程 + 队列"，实际实现采用**多线程 + 队列**，原因：
>
> 1. `onnxruntime`（OCR）与 `llama.cpp`（推理）在计算时都会释放 GIL，
>    因此线程同样能获得真正的多核并行；
> 2. Windows 上 `multiprocessing` 使用 spawn 启动子进程，每次都要重新导入
>    PyQt6 与全部依赖（数秒），且模型权重需在每个子进程中各加载一份，
>    内存开销成倍增加 —— 这与"8GB 内存可运行"的产品目标直接冲突；
> 3. 子进程与 Qt 主进程之间传递 numpy 图像需要序列化拷贝，在 15fps 下
>    会带来可观的 CPU 与内存带宽开销。
>
> 队列解耦、背压与丢帧策略完全保留，架构的分层与解耦特性不变。

### 从捕获到渲染的完整链路

1. **捕获**：`mss` 抓取桌面 → 与上一帧做灰度差分 → 提取变化区域包围盒
2. **OCR**：对变化区域做小字号增强 → `RapidOCR` 识别 → 包围盒叠加帧原点得到物理坐标
3. **后处理**：按垂直重叠聚类成行 → 合并行内相邻块 → 按间距划分段落 → 去重、过滤噪声、修复断词
4. **术语替换**：命中的术语替换为 Unicode 私用区占位符
5. **缓存查询**：命中直接返回，跳过推理；条目同时写入 SQLite 持久层，重启后跨会话仍命中
6. **调度**：按手动 / 资源 / 内容三级策略选定模型
7. **推理**：多个片段合并为一次请求，用分隔符对位
8. **解析与还原**：切分输出并校验片段数，失败则降级逐条翻译；还原术语占位符
9. **坐标映射**：物理坐标 → 显示器逻辑坐标 → 窗口内局部坐标
10. **渲染**：自适应字号与换行 → 绘制背景遮罩与文字 → 分发到对应显示器的透明层

### 高 DPI 坐标对齐

这是原位翻译最容易出错的地方，程序中显式区分两套坐标系：

- **物理坐标**：`mss` 位图坐标，以虚拟桌面左上角为原点，单位物理像素；
- **逻辑坐标**：Qt 窗口与鼠标事件坐标，已按缩放比例折算。

换算遵循 Qt `QHighDpiScaling` 的规则：**屏幕原点不缩放，只缩放尺寸**。

```
逻辑坐标 = 屏幕物理原点 + (物理坐标 - 屏幕物理原点) / 缩放比例
```

若把原点也除以缩放比例（一个很自然的错误），150% 缩放的副屏上的译文会
整体偏移数百像素甚至被推出窗口。`tests/test_geometry.py` 中有针对该规则
的专项回归测试。

## 设计说明

界面设计遵循两套公开规范，详细说明见 [`docs/UI设计规范.md`](docs/UI设计规范.md)。

### mozilla/OpenDesign（MPL-2.0；设计作品 CC0-1.0）

采纳其"把开源原则带入创意设计"的主张，落实为四项工程约定：

1. **交付设计源文件** —— 设计令牌（`ui/design/tokens.py`）与设计规范文档
   本身即为可编辑的设计源文件，而非无法修改的截图；
2. **开放可复用** —— 设计令牌以 CC0 精神公开；
3. **隐私与信任优先** —— 界面如实呈现"全离线"承诺，不设诱导性文案；
4. **无障碍作为硬约束** —— 正文对比度满足 WCAG AA，关键状态不依赖颜色
   单独传达（状态点旁始终有文字）。

### emilkowalski/skills（设计工程规范）

动效数值逐项取自规范，未自行发明近似值：

- **缓动曲线**：`ease-out` = `cubic-bezier(0.23, 1, 0.32, 1)`，
  `ease-in-out` = `cubic-bezier(0.77, 0, 0.175, 1)`；
- **时长**：按钮按下 160ms、工具提示 125ms、弹出层 200ms、模态 250ms、
  通知 400ms，界面动效一律不超过 300ms；
- **按下反馈**：缩放至 0.97；
- **进入动效**：从 `scale(0.95)` + 透明开始，**绝不从 `scale(0)` 开始**；
- **频率闸门**：热键等高频操作（每天上百次）**不加任何动画**；
- **减少动态效果**：保留不透明度过渡，去掉位移与缩放。

### 关键设计决策：译文层不做动画

译文层最高以 15fps 刷新。按动效规范的频率闸门，**高频刷新的数据展示区域
不应加入入场或位移动画**：一方面动画会让正在阅读的文字持续位移，破坏原位
对照；另一方面每秒十余次的动画重建会直接拖垮渲染性能。

因此译文层的更新是**瞬时替换**，只在"整层显示/隐藏"这类低频操作上使用
淡入淡出。

## 已知限制

诚实地列出当前版本尚未完成或存在限制的部分：

1. **语言覆盖有限**。142 个选项不代表全部可靠可用。0.6.13全量实际尝试含失败，
   0.6.14修复了Indic组合附标误判代码而跳过翻译及启动误杀推理服务的问题；
   详见`docs/measurements/language_functional_audit_20261006.md`。手动 OCR
   有 11 个识别模型，对没有模型的脚本明确报错；自动模式使用一个中英日模型，
   不进行通用语言检测。冷门语言的翻译身份及语义仍需核查。
2. **GPU 显存监控依赖 `pynvml` 且仅支持 NVIDIA**。未安装时资源自适应
   退化为仅依据 CPU 与渲染帧率决策，功能不受影响但精度降低。
3. **跨屏框选会被裁剪到单块显示器内**。因为跨屏矩形的位图会被显示器
   间隙破坏，导致坐标换算失准。
4. **竖排文字（日语/中文古籍）未做专门适配**，OCR 后处理按横排假设组织
   文本行。
5. **仅支持 Windows**。macOS 与 Linux 适配在规划中，需要替换屏幕捕获、
   全局热键与透明窗口三处平台相关实现。
6. **`mypy` 未覆盖 UI 层**。Qt 的信号槽与动态属性难以静态推断，
   强行检查会引入大量无意义报错。
7. **未在真实多屏高 DPI 环境下做过完整实机验证**。坐标换算逻辑已通过
   单元测试覆盖，但真机行为仍受显卡驱动影响。
8. **300ms 端到端 p95 目标尚未确认达成**。OCR 单项暖推、缓存命中延迟和
   同时运行两个模型的组合测试耗时，都不能代替单应用新字幕的端到端统计。

## 隐私声明

- 屏幕捕获、文字识别、大模型推理、原位渲染**全部在本机完成**；
- **不发起任何与翻译相关的网络请求**，无遥测、无数据上报、无云端依赖；
- 翻译历史保存在本机应用数据目录的 SQLite 数据库中，不参与任何同步；
- **日志不记录屏幕识别文本与翻译结果的内容**，仅记录字符数等元信息
  （见 `utils/logger.py` 的 `describe_text`）；
- 用户可在设置中关闭"记录原文"，此时仅保存译文。

> 唯一的例外：RapidOCR 组件首次运行时可能需要下载 ONNX 模型文件。
> 该下载可通过预先放置模型文件的方式避免，之后即不再联网。
